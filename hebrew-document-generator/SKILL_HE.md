# מחולל מסמכים בעברית

## הבהרה משפטית

כלי זה הוא כלי מידע חינמי, הפועל באמצעות מודל בינה מלאכותית. הוא מסדר ומעצב מסמכים בעברית (PDF, Word ו-PowerPoint) לפי התוכן שאתם מספקים, ומציג מבני סעיפים ושדות מקובלים לחוזה, לחשבונית, לקבלה ולהצעת מחיר. כל תוצריו מופקים באופן אוטומטי על ידי מודל בינה מלאכותית, ללא מעורבות, בדיקה או אישור של עורך דין, יועץ מס או רואה חשבון. הפלט אינו ייעוץ משפטי, אינו חוות דעת משפטית ואינו מסמך שנערך על ידי עורך דין, אלא תבנית עימוד שאתם ממלאים ומתאימים בעצמכם: הכלי אינו בודק את נסיבות העסקה שלכם, אינו בוחן את תוקפם או את אכיפותם של הסעיפים ואינו מתאים אותם לדין החל עליכם. מודל בינה מלאכותית עלול לשגות, להשמיט נתונים או להציג מסקנה שגויה.

כל נוסח שהכלי מנסח הוא טיוטה אוטומטית לצורכי התארגנות אישית בלבד. אין בו מסמך שנערך על ידי עורך דין, ואין להסתמך עליו כראיה. דוגמאות החשבונית והקבלה הן דוגמאות עימוד בלבד ולא מסמכי מס שהופקו. האחריות לדיווח ולתשלום המס היא שלכם, החישוב המחייב הוא של רשות המסים, וייצוג מול רשות המסים שמור למי שרשאי לכך לפי דין. הכלי אינו מהווה תחליף לייעוץ המתחשב בנתונים ובצרכים המיוחדים של כל אדם, ולפני נקיטת הליך, חתימה על מסמך או הגשה לרשות או לבית משפט יש לפנות לעורך דין. כל שימוש בפלט ובתוצריו הוא באחריותו הבלעדית של המשתמש.

### שלב 3: PDF בעברית עם reportlab

תסתכלו על `scripts/generate_doc.py` לפייפליין המלא של היצירה.

```python
from reportlab.lib.pagesizes import A4
from reportlab.pdfgen import canvas
from reportlab.pdfbase import pdfmetrics
from reportlab.pdfbase.ttfonts import TTFont
from reportlab.lib.units import mm
from bidi.algorithm import get_display  # NOT `from bidi import get_display`, see below

# רישום גופן עברי
pdfmetrics.registerFont(TTFont('Heebo', 'Heebo-Regular.ttf'))
pdfmetrics.registerFont(TTFont('Heebo-Bold', 'Heebo-Bold.ttf'))

def create_hebrew_pdf(filename, title, content_lines):
    c = canvas.Canvas(filename, pagesize=A4)
    width, height = A4

    # כותרת -- יישור לימין עבור RTL
    c.setFont('Heebo-Bold', 18)
    hebrew_title = get_display(title)
    c.drawRightString(width - 20*mm, height - 30*mm, hebrew_title)

    # שורות תוכן
    c.setFont('Heebo', 12)
    y = height - 50*mm
    for line in content_lines:
        display_line = get_display(line)
        c.drawRightString(width - 20*mm, y, display_line)
        y -= 7*mm

    c.save()
```

נקודות חשובות ל-reportlab בעברית:
- תמיד להשתמש ב-`get_display()` מ-python-bidi לסידור מחדש של תווים
- להשתמש ב-`drawRightString()` לטקסט RTL מיושר לימין
- לרשום גופני TTF עבריים במפורש - ל-reportlab אין תמיכה מובנית בעברית
- לקבוע גובה שורה של לפחות 1.5 מגודל הגופן לקריאות בעברית
- ייבוא python-bidi: תייבאו מ-`bidi.algorithm`. בגרסה 0.6.x יש שני מימושים. `bidi.algorithm` הוא מימוש הפייתון, התואם לגרסאות קודמות, והוא משקף סוגריים. הייבוא העליון `from bidi import get_display` עוטף ספריית Rust שמדלגת על כלל השיקוף (issue #25 בפרויקט), ולכן `(18%)` מודפס כ-`)18%(` ב-PDF של reportlab, וכל סוגריים בשורה עברית יוצאים הפוכים. גרסה 0.6.x דורשת פייתון 3.9 ומעלה.
- טקסט רב-שורתי: `drawRightString()` מצייר שורה אחת ולא גולש. אל תעבירו פלט של `get_display()` ל-`Paragraph` של reportlab: הוא גולש את המחרוזת שכבר הופכה, ולכן המשפט האחרון נוחת בשורה העליונה, ו-`wordWrap='RTL'` בלי bidi מדפיס כל מילה עם אותיות הפוכות. קודם גולשים בסדר הלוגי, ורק אז מריצים `get_display()` על כל שורה גמורה: הפונקציות `wrap_hebrew_lines()` ו-`draw_hebrew_paragraph()` ב-`scripts/generate_doc.py` עושות את זה. למסמכים ארוכים וזורמים (חוזים), WeasyPrint (שלב 4) גולש עברית באופן מובנה.

### שורות מעורבות עברית / לטינית / ספרות

הכשל הנפוץ ביותר ב-RTL במסמכים מיוצרים הוא שורה שמערבת תיאור בעברית עם מספרים LTR וסמל מטבע, למשל שורת פריט בחשבונית. `get_display()` מטפל בסידור הדו-כיווני, אבל צריך להעביר את *כל המחרוזת הלוגית* בקריאה אחת כדי שהאלגוריתם יראה את ההקשר המלא:

```python
from bidi.algorithm import get_display

# סדר לוגי: תיאור בעברית, אחר כך כמות, מחיר ליחידה, מטבע
line = 'ייעוץ טכני (3 שעות) - 1,500.00 ש"ח'
c.setFont('Heebo', 11)
c.drawRightString(width - 20 * mm, y, get_display(line))
```

הספרות, הפסיק, הנקודה והסוגריים נוחתים כולם במקום הנכון כי האלגוריתם הדו-כיווני פותר אותם ביחס לעברית שמסביב (ו-`bidi.algorithm` משקף את הסוגריים). אל תפצלו את השורה לחלקים ותסדרו אותם בעצמכם, ואל תקראו ל-`get_display()` רק על החלק העברי, שתי הגישות שוברות את סדר המספרים.

from weasyprint import HTML

html_content = """

  @font-face {
    font-family: 'Heebo';

  }

  table {
    width: 100%;
    border-collapse: collapse;
  }
  th, td {
    border: 1px solid #333;
    padding: 6px 10px;
    text-align: start;
  }
</style>
</head>
<body>
  <h1>חשבונית מס</h1>
  <!-- תוכן המסמך כאן -->
</body>

### שלב 5: DOCX בעברית עם python-docx

ב-DOCX עברית ואנגלית מעורבות נשברות הכי הרבה. הטיפול של Microsoft Word בטקסט דו-כיווני שונה מ-LibreOffice, מ-Preview/Quick Look של macOS ומרוב המציגים, שמרנדרים פלט סלחני ש**מסתיר** באגים שקיימים רק ב-Word, ולכן בודקים ב-Word עצמו. תשתמשו בסקריפט המצורף `scripts/docx_rtl.py` (העתיקו אותו ליד הקוד שלכם או ייבאו אותו); הוא מממש את הכללים האלה:

1. **כיוון פסקה:** שורה עם עברית כלשהי מקבלת `<w:bidi/>` (בסיס RTL) **בלי יישור מפורש**. `w:jc` הוא לוגי, ולכן `jc=right` בפסקת RTL פירושו סוף השורה, ש-Word מצייר בצד **שמאל**. פסקת RTL בלי `jc` מתחילה בימין הוויזואלי. שורה באנגלית בלבד מקבלת בסיס LTR ויישור לשמאל.
2. **פיצול runs לפי סקריפט, `<w:rtl/>` על ה-runs העבריים, אף פעם לא על runs של לטינית או ספרות.** בלי `<w:rtl/>` על ה-runs העבריים, Word מסדר את ה-runs של שורה מעורבת משמאל לימין: `ההסכם נחתם בין חברת Acme בע"מ` יוצא עם הצירופים בסדר הפוך. כשמילה לטינית או מספר נמצאים **בתוך** run מסומן rtl, Word הופך אותם (`7/2023` הופך ל-`2023/7`). לכן ספרות יוצרות runs משלהן, מפרידים בין ספרות (`1,500.00`, `03-1234567`) וסימני `%` ומטבע נשארים עם המספר, מספר שבא אחרי מילה לטינית (`KI-67`) מצטרף אליה, סימן `+`/`-` מוביל מצטרף למספר שלו (`+972-3-1234567`), וסוגריים ופיסוק בין שני הסקריפטים עוברים לצד העברי, כך ש-`(גרסה 2).` שומר על הסוגר והנקודה במקומם. היוצא מן הכלל הוא זוג סוגריים סביב טקסט לטיני שבא מיד אחרי מילה לטינית (`Acme (Israel)`, `Office (365)`): הוא נשאר עם ה-run הלטיני, אחרת Word משקף את סוגר הסגירה לתוך ה-run העברי. אותיות מסווגות לפי מחלקת ה-bidi שלהן ב-Unicode, כך שאותיות לטיניות עם סימנים (`Nestlé`) נשארות מילה אחת. סימון רשימה בתחילת שורה (`2.`, `10.`) מתמזג ל-run העברי כדי שהנקודה לא תקפוץ ל-`.2`.
3. **תכונות סקריפט מורכב על כל run:** גופן `w:cs` וגודל `w:szCs` (Word מחיל את `w:ascii`/`w:sz` רק על טקסט לטיני), ו-`w:bCs`/`w:iCs` לצד `w:b`/`w:i`. השמטה של `w:cs`/`w:szCs` היא הבאג הקלאסי של "הגופן/הגודל שהגדרתי לא עשה כלום".
4. **לעולם לא מכניסים סימני כיווניות או isolates של Unicode** (U+200E, U+2066-2069): Word מצייר אותם כריבועים גלויים בגופן David.

```python
import sys
sys.path.insert(0, 'scripts')  # wherever docx_rtl.py lives
from docx_rtl import new_hebrew_document, add_rtl_paragraph, add_rtl_table

doc = new_hebrew_document(font='David', size=12)   # also sets <w:bidi/> on the section
add_rtl_paragraph(doc, 'חוזה שירותים', size=18, bold=True)
add_rtl_paragraph(doc, 'ההסכם נחתם ביום 13/01/2026 בין חברת Acme בע"מ לבין הלקוח (גרסה 2).')
add_rtl_paragraph(doc, '2. תמורה', bold=True)
add_rtl_table(doc, ['תיאור', 'כמות', 'מחיר', 'סה"כ'],
              [['ייעוץ טכני (3 שעות)', 1, '1,500.00', '1,500.00'],
               ['פיתוח Acme', 2, '600.00', '1,200.00']])
doc.save('contract.docx')
```

הפקודה `python scripts/docx_rtl.py --output sample.docx` כותבת קובץ דוגמה שמפעיל את כל הכללים. כל האמור נבדק מול הרינדור של Microsoft Word עצמו (Word 16.113 ל-Mac, בייצוא ל-PDF של Word עצמו).

**אל תקראו ל-`get_display()` על טקסט של DOCX.** Word מריץ את האלגוריתם הדו-כיווני בעצמו, ולכן עיבוד מקדים מפעיל אותו פעמיים ומשבש את השורה. `get_display()` שייך רק למסלול של reportlab.

**כותרות עליונות, כותרות תחתונות ורשימות ממוספרות** הם "סיפורים" נפרדים במסמך: ממלאים את הפסקאות שלהם באותו היגיון (הפונקציה `_fill_paragraph(p, text, font, size)` של המודול עובדת על כל אובייקט פסקה, למשל `section.footer.paragraphs[0]`).

### טבלאות בעברית ב-DOCX (התיקון ל"הטבלה יוצאת הפוכה")

טבלה הפוכה (העמודה הלוגית הראשונה, למשל `תיאור`, בצד **שמאל**) היא באג של **סדר עמודות**, לא של כיוון טקסט. לטבלאות של python-docx אין `<w:bidiVisual/>`, ולכן Word מסדר את העמודות משמאל לימין. טבלה עברית צריכה את **שני** התיקונים, ו-`add_rtl_table` מחיל את שניהם:

1. **סדר העמודות:** `table.table_direction = WD_TABLE_DIRECTION.RTL` פולט `<w:bidiVisual/>`, והעמודה הלוגית הראשונה מצוירת מימין. `table.alignment = WD_TABLE_ALIGNMENT.RIGHT` מצמיד את בלוק הטבלה לשוליים הימניים.
2. **הטקסט בתא:** כל תא הוא פסקה נפרדת, ולכן הוא מקבל `<w:bidi/>` ואת ה-runs לפי סקריפט מכלל 2, **בלי** יישור מפורש. הגדרת יישור "ימין" בתאי RTL דוחפת את העברית לשמאל הוויזואלי בזמן שתאי המספרים נשארים בימין (הבאג של v1.7.0).

שמרו את הכותרות והשורות בסדר לוגי; היפוך עצמי של רשימות העמודות הופך פעמיים ברגע ש-`bidiVisual` מוגדר. ב**בלוק סיכומים של חשבונית** תא התווית בדרך כלל משתרע על כמה עמודות דרך `row.cells[a].merge(row.cells[b])`; טווח ממוזג עלול לנחות בצד הלא נכון תחת `bidiVisual`, אז בדקו את השורה הממוזגת ב-Word.

### שלב 6: PPTX בעברית עם pptxgenjs

```javascript
const pptxgen = require('pptxgenjs');
const pptx = new pptxgen();

pptx.layout = 'LAYOUT_16x9';
pptx.rtlMode = true;

const slide = pptx.addSlide();

// כותרת בעברית
slide.addText('סקירה רבעונית', {
  x: 0.5, y: 0.5, w: '90%', h: 1.0,
  fontSize: 28,
  fontFace: 'Heebo',
  color: '1a1a2e',
  align: 'right',
  rtlMode: true,
  lang: 'he-IL',   // default is en-US: PowerPoint would spell-check the Hebrew as English
  bold: true,
});

// נקודות תבליט בעברית
slide.addText([
  { text: 'תוצאות כספיות', options: { bullet: true, rtlMode: true } },
  { text: 'יעדים לרבעון הבא', options: { bullet: true, rtlMode: true } },
  { text: 'סיכום פעילות', options: { bullet: true, rtlMode: true } },
], {
  x: 0.5, y: 2.0, w: '90%', h: 3.0,
  fontSize: 18,
  fontFace: 'Heebo',
  align: 'right',
  rtlMode: true,
  lang: 'he-IL',
});

pptx.writeFile({ fileName: 'quarterly-review.pptx' });
```

**לטבלאות PPTX** יש אותו עניין של סדר עמודות RTL כמו ב-DOCX. pptxgenjs מציג את עמודות הטבלה לפי הסדר שבמערך ה-`rows` שלכם, הוא אינו משקף אוטומטית עבור RTL. כדי שהעמודה הלוגית הראשונה תיקרא מימין, הפכו את סדר התאים בכל שורה בנתונים, והגדירו `rtlMode: true` (וגם `align: 'right'`) על ה-`options` של כל תא כדי שהטקסט בתוך כל תא ייושר לימין ויטופל מבחינת bidi:

```javascript
// עמודות לוגיות: תיאור | כמות | מחיר. הופכים בכל שורה כדי שעמודה 1 תוצג מימין
const headers = ['תיאור', 'כמות', 'מחיר'];
const dataRows = [['ייעוץ', '1', '1,500.00']];
const opt = { rtlMode: true, align: 'right', fontFace: 'Heebo', lang: 'he-IL' };
const tableRows = [headers, ...dataRows].map(
  row => [...row].reverse().map(text => ({ text, options: opt }))
);
slide.addTable(tableRows, { x: 0.5, y: 1.5, w: 9 });  // rtlMode is a per-cell text option, not a table option
```

שימו לב לקונבנציה ההפוכה מ-DOCX: python-docx חושף היפוך עמודות ויזואלי אמיתי (`table_direction = RTL`) ולכן שומרים את הנתונים בסדר לוגי, בעוד של-pptxgenjs אין דגל כזה, ולכן הופכים את העמודות בנתונים בעצמכם. אמתו את השקופית המוצגת.

## מלכודות נפוצות
- צריך להפעיל את `get_display()` שורה-שורה בזמן הציור, מיד לפני `drawRightString()`, ולא פעם אחת על מסמך או בלוק רב-שורתי שלם. האלגוריתם הדו-כיווני אינו אידמפוטנטי: הרצה שלו על טקסט שכבר סודר מחדש הופכת את התווים פעמיים ומפיקה פלט משובש. טעות נפוצה של סוכנים היא "לעבד מראש" רשימה שלמה של שורות דרך `get_display()` ואז לקרוא לו שוב בתוך לולאת הציור.
- מחוללי PDF נוטים לכיוון טקסט LTR כברירת מחדל. מסמכים בעברית חייבים כיוון פסקה RTL, וטקסט מעורב עברית-אנגלית צריך תמיכה תקינה באלגוריתם BiDi.
- ל-DOCX (python-docx) יש מלכודת הפוכה מ-PDF: אל תריצו `get_display()` על הטקסט, Word מפעיל את אלגוריתם ה-bidi בעצמו. הכשלים שמפיקים קובץ Word עברי "שבור" הם (א) שורה מעורבת שלמה ב-run אחד המסומן `<w:rtl/>` (מספרים ואנגלית מתהפכים), (ב) שורות מעורבות **בלי** `<w:rtl/>` על ה-runs העבריים (הצירופים יוצאים בסדר הפוך), (ג) `jc=right` על פסקאות RTL (טקסט מיושר לשמאל), ו-(ד) בלי גופן `w:cs` / גודל `w:szCs` של סקריפט מורכב (הגופן והגודל לא חלים על העברית). הסקריפט `scripts/docx_rtl.py` נמנע מכל הארבעה.
- ב-PDF של reportlab, הייבוא `from bidi import get_display` (מימוש ה-Rust) לא משקף סוגריים, ולכן כל `(...)` בעברית מודפס הפוך. תייבאו מ-`bidi.algorithm`.
- הוספה ידנית של run לפסקה עברית קיימת (למשל שורת חתימה) מדלגת על הפיצול לפי סקריפט ועל דגל `<w:rtl/>`. בנו את כל השורה עם `add_rtl_paragraph` במקום.
- טבלת DOCX עברית הפוכה (העמודה הראשונה בצד שמאל) היא באג של סדר עמודות, לא של כיוון הטקסט. העוזר `add_rtl_paragraph` ו-bidi לתאים לא עושים לזה דבר: לטבלאות python-docx אין `<w:bidiVisual/>`, ולכן Word מסדר עמודות LTR. הגדירו `table.table_direction = WD_TABLE_DIRECTION.RTL` על הטבלה וגם העבירו כל תא דרך עוזר ה-bidi לתאים, צריך את שניהם (העוזר `add_rtl_table` עושה את שניהם). שמרו את נתוני העמודות בסדר לוגי, היפוך עצמי שלהם הופך פעמיים ברגע ש-`bidiVisual` מוגדר.
- סוכנים עלולים לבחור גופנים בלי תמיכה בתווים עבריים (Arial עובד, אבל הרבה גופנים דקורטיביים לטיניים לא). תמיד תוודאו שהגופן כולל את טווח ה-Unicode העברי (U+0590-U+05FF).
- פורמט התאריך בעברית הוא DD/MM/YYYY בהקשר חילוני, ותאריכים עבריים (ט"ו באדר תשפ"ו למשל) למסמכים דתיים/מסורתיים. סוכנים עלולים ללכת ל-MM/DD/YYYY כברירת מחדל.
- מסמכים משפטיים בישראל דורשים עיצוב מסוים: לא משתמשים בניקוד בעברית עסקית/משפטית רגילה. סוכנים עלולים להוסיף ניקוד כי הם חושבים שזה משפר את הבהירות, אבל בפועל זה נראה לא מקצועי במסמכים רשמיים.

## פתרון בעיות

### שגיאה: "תווים עבריים מוצגים כריבועים או סימני שאלה"
סיבה: גופן עברי לא רשום או לא קיים במערכת
פתרון: תורידו גופן TTF עברי (Heebo מ-Google Fonts למשל), רשמו אותו עם `pdfmetrics.registerFont()` ל-reportlab, או התקינו אותו כגופן מערכת ל-WeasyPrint.

### שגיאה: "הטקסט מוצג משמאל לימין במקום מימין לשמאל"
סיבה: חסר סידור bidi או הגדרת כיוון RTL
פתרון: ב-reportlab, תפעילו `get_display()` מ-`bidi.algorithm`. ב-python-docx, תבנו פסקאות עם `scripts/docx_rtl.py` (מגדיר `<w:bidi/>` על הפסקה ו-`<w:rtl/>` על ה-runs העבריים). ב-WeasyPrint, תוודאו `dir="rtl"` על אלמנט ה-HTML.

### שגיאה: "מספרים וסימני פיסוק במיקום שגוי"
סיבה: אלגוריתם הטקסט הדו-כיווני לא מטפל נכון בתוכן מעורב עברית/מספרים
פתרון: ב-reportlab, מעבירים את כל המחרוזת הלוגית דרך `get_display()` מ-`bidi.algorithm` בקריאה אחת (ראו "שורות מעורבות עברית / לטינית / ספרות"); סוגריים שיוצאים `)...(` מעידים שנעשה שימוש בייבוא ה-Rust העליון. ב-WeasyPrint, מגדירים `dir="rtl"` על אלמנט ה-`<html>` ומעבירים את הטקסט בסדר לוגי: מנוע הטקסט שלו פורס את השורה מהסדר הלוגי (נבדק עם WeasyPrint 70, אף שהתיעוד של WeasyPrint עדיין מונה טקסט דו-כיווני בין התכונות שאינן נתמכות), ולכן לעולם לא מסדרים מראש טקסט HTML עם `get_display()`, ובודקים את ה-PDF שנוצר. ב-DOCX/python-docx עושים את ההפך מתיקון ה-PDF: לעולם לא קוראים ל-`get_display()` (Word מסדר בעצמו). מגדירים `<w:bidi/>` על הפסקה, מפצלים את השורה ל-runs לפי סקריפט, מסמנים `<w:rtl/>` רק את ה-runs העבריים, ומגדירים גופן `w:cs` וגודל `w:szCs` על כל run (ראו שלב 5).

### שגיאה: "קובץ Word עברי מציג אנגלית בצד הלא נכון, או שהגופן/הגודל מתעלמים"
סיבה: כל השורה המעורבת ב-run אחד המסומן `<w:rtl/>` (אנגלית ומספרים מתהפכים), ה-runs העבריים של שורה מעורבת בלי `<w:rtl/>` (צירופים בסדר הפוך), או שה-runs מגדירים רק `w:ascii`/`w:sz` ולא את `w:cs`/`w:szCs` של הסקריפט המורכב (העברית מתעלמת מהגופן/הגודל). בדיקת נוכחות פשוטה של `<w:rtl/>` עוברת גם על קובץ שעדיין מרונדר שבור, אז תבדקו את מבנה ה-runs ולא רק את הדגל.
פתרון: השתמשו ב-`scripts/docx_rtl.py` (שלב 5): פיצול runs לפי סקריפט, rtl רק על ה-runs העבריים, `w:cs` + `w:szCs` על כל run.

### שגיאה: "טבלה ב-Word (.docx) יוצאת הפוכה, העמודה הראשונה בצד שמאל"
סיבה: זהו באג של סדר עמודות, לא של כיוון הטקסט. טבלאות python-docx נוצרות ללא `<w:bidiVisual/>` על `<w:tblPr>`, ולכן Word מסדר את העמודות משמאל לימין והעמודה הלוגית הראשונה נוחתת בצד שמאל, מה שגורם לכל הטבלה להיקרא לאחור. תיקון הטקסט בתוך כל תא אינו מזיז את העמודות.
פתרון: הגדירו `table.table_direction = WD_TABLE_DIRECTION.RTL` פעם אחת לכל טבלה (פולט `<w:bidiVisual/>`, שמשקף את סדר העמודות הוויזואלי ל-RTL), וגם העבירו את הטקסט של כל תא דרך עוזר ה-bidi לתאים. שניהם נחוצים, ו-`add_rtl_table` עושה את שניהם. שמרו את נתוני הכותרות/השורות בסדר לוגי טבעי, אל תהפכו את רשימת העמודות בעצמכם, זה הופך פעמיים ברגע ש-`bidiVisual` מוגדר. אמתו ב-Word, לא ב-LibreOffice/Preview (הם משקפים טבלאות בסלחנות רבה יותר ומסתירים זאת).

### שגיאה: "תאי טבלה עברית מיושרים לשמאל (כותרות/טקסט בשמאל, מספרים בימין)"
סיבה: הוגדר יישור `RIGHT` פיזי על פסקאות התא. `w:jc` ב-OOXML הוא לוגי, לא פיזי: `right` פירושו "סוף השורה", ובפסקה עברית (`<w:bidi/>`) השורה מסתיימת בשמאל, ולכן יישור RIGHT דוחף את העברית לשמאל הוויזואלי בעוד תאי מספרים (LTR) עדיין הולכים ימינה, ומשאיר טבלה משוננת ולא מיושרת.
פתרון: אל תגדירו שום יישור מפורש על תאי טבלת RTL. תנו לכל פסקת תא `<w:bidi/>` והשאירו את היישור לא מוגדר, פסקת RTL מתיישרת כברירת מחדל לקצה ה-START שלה (הימין הוויזואלי), כך שכותרות, טקסט עברי ומספרים מתיישרים צמוד לימין. ראו `set_cell_rtl_text` ב-`scripts/docx_rtl.py`.

### שגיאה: "כל הפסקאות העבריות בקובץ ה-Word מיושרות לשמאל"
סיבה: לפסקאות יש `<w:bidi/>` וגם יישור ימין מפורש (`WD_ALIGN_PARAGRAPH.RIGHT`, כלומר `w:jc="right"`). `jc` הוא לוגי, ולכן בפסקת RTL "ימין" הוא סוף השורה, השמאל הוויזואלי.
פתרון: משאירים את היישור לא מוגדר בפסקאות RTL; הן מתחילות בימין הוויזואלי. הסקריפט `scripts/docx_rtl.py` עושה את זה.

### שגיאה: "WeasyPrint: cannot load library 'libgobject-2.0-0'" או שה-PDF יוצא בגופן בלי עברית
סיבה: Pango לא מותקן או לא נמצא בנתיב הספריות, או שה-HTML רונדר בלי `base_url` ולכן כתובת יחסית ב-`@font-face` נזנחה.
פתרון: מתקינים Pango (שלב 2) ומעבירים `base_url` ל-`HTML(...)` (שלב 4).
